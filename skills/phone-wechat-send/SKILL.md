## v1.2 改动（2026-10-26，对抗审查后）

- 新增发送前气泡基数：发送前记下已发出气泡数和最底部已发出消息，发送后必须恰好加一，否则不算成功。
- 新增进入时空输入检查：进入目标会话后、切输入法之前，先查输入框。非空就停下，不清空、不发送、原样汇报。
  这条取代旧公开版“超时后已有目标文字就只点发送”的说法：输入框里的文字来源无法证明是谁打的，
  自动把它发出去等于替用户把草稿发出去，所以 v1.2 一律先停下，等用户在新的一轮里明确授权再处理。
- 新增点发送前二次标题核对：标题只在进会话时查一次不够，点发送前必须在同一屏再读一次标题和输入框，两者都对才能点。
- 新增真人收件分支：默认只做文件传输助手这类自测会话。给真人、真群发消息时，任务提示里必须同时写明收件人、完整内容、
  以及用户当次的明确确认，缺任何一项就停下；标题相等不能代替这个确认。
- 新增单例锁：每次运行必须带调用方给的运行标识（run-id，例如日期时间），阶段通知里带上它；
  开始前先查锁文件，锁存在就停下，不要并发跑第二趟。锁的路径和写法见“单例与运行标识”。
- 新增崩溃后清理清单：进程被杀、超时后，skill 文本本身保证不了清理，调用方必须按“中断后调用方核对清单”逐项核对，
  不能默认输入法、输入框、气泡都已恢复。
- 合并旧分叉：服务器正本此前缺“超时与中断”一节，公开版缺示例一节，v1.2 两份内容对齐，只差作者一行脱敏。

## v1.3 改动（2026-10-26，定位混合规则）

- 新增“先结构、后截图”混合规则：同一屏状态下先调一次 `ui()`，节点非空且找到目标节点时用节点范围点按和核对；
  节点为空或目标不在节点里时，立刻切到 `screen()` 文字框加截图，不要在同一屏上反复重试 dump。
  这条不用新工具，只是把现在的 fallback 写死：通用 app 上更稳，微信上不亏（微信结构树经常为空，fallback 就是主路）。
- 新增 dumpsys 辅助核对：用 `dumpsys` 确认当前应用和页面（例如包名是否为微信），只能当辅助核对，
  不能当点按依据、不能代替标题关卡、不能代替会话身份——dumpsys 给不了会话行、输入框的精确坐标，
  活动名也只能证明进了微信主界面，不能证明进了哪一个会话。
- 明确过期规则：滚屏、点按、等待稳定后屏幕状态已变，上一屏的节点、坐标、文字框一律作废，
  下一步动手前必须重新调 `ui()` 或 `screen()`，不准用旧坐标点新屏。

## v1.3.1 改动（2026-10-26，v1.3 实发 retest 后硬化，未改主流程）

这次 retest 暴露的都不是主流程错误，而是预检、计数和残留处理上的歧义，v1.3.1 只把它们写死：

- 新增会话列表草稿早停：进会话之前先看会话列表，目标行若带草稿标记（例如“[草稿]”），
  在进会话之前就停下，不要为了“进去确认一下”再点会话。进去之后输入框非空同样停下，两条是同一规则的两个关卡，
  早停只是少一次不必要的导航。草稿哪怕只是目标消息的一个字前缀，也按非空处理：
  不补打剩余部分、不顺手把框里那条发出去，除非用户在新的一轮里明确授权处理这条草稿。
- 新增残留输入法判定：任务开始时若当前输入法已经是临时用的微信输入法，且没有正在跑的任务和单例锁，
  这就是上一趟被杀、超时留下的残留，不是用户的正常输入法。调用方应先把它恢复回用户正常输入法并读回确认，
  再开跑；不要把残留的微信输入法当成“原始输入法”记录下来，那样收尾会把残留状态原样留下来。
  2026-10-26 retest 前预检就发现了这一项，恢复回搜狗后才开跑。
- 改写气泡计数口径（v1.2 的“可见气泡数”会数出两个口径）：从 v1.3.1 起必须同时记两个数——
  一是文字逐字等于目标消息的气泡数，二是全部已发出气泡数；发送前和发送后都要先滚到顶部、再滚到底部全量数，
  不能只数当前屏可见的那几条。成功条件是两个数都恰好加一：目标数加一证明新消息就是目标，
  总数也只加一证明没有多发别的东西。只数其中一个、或只数可见部分，都不算核对通过。
  2026-10-26 retest 里 Hermes 数的是总数 5 变 6、Muse 数的是“你好”数 4 变 5，两个口径都加一才算对齐。
- 写死三条已知 fallback，不再当成“报错”反复处理：`open_app("微信")` 中文别名未命中时，只改包名
  `com.tencent.mm` 再试一次，不要反复试别名；dumpsys 管道里的 `grep` 无匹配会返回非零退出码，
  命令里必须加 `|| true` 兜底，不要把 grep 无匹配当成任务失败；Linux 端不要调 `screen_info()`，
  它在 Linux 上会报 Quartz 模块缺失，直接用 `screenshot()` 配合视觉核对。
- 单例锁路径实发验证通过：2026-10-26 retest 里锁写了也删了，调用方事后核对锁已不存在，
  v1.2 里“锁路径未经过实发验证”的保留说法从此作废；残留锁仍按 fail-closed 处理，见“单例与运行标识”。
- 新增调用方开跑前预检一节（见下文）：adb、默认模型、输入法、锁、残留任务、会话列表草稿、
  以及核对截图必须确实是微信前台，这几项是 Hermes 任务开始前由调用方做的，不在 Hermes 任务内补做。

## v1.3.2 改动（2026-10-26，任务期间临时常亮，未实发验证）

背景：手机当前屏幕超时为 600000 毫秒（10 分钟），而一趟完整任务量级为 7 分 44 秒到接近 10 分钟，
刚好卡在边界上，任务中途无人碰手机时屏幕可能变暗甚至灭屏。本节只加常亮逻辑，不动主流程、不引新工具，
走的仍是 skill 里已在用的 `shell()` 读写设置，处理标准与恢复输入法完全相同。

- 开始时（第 1 步，写锁之后、打开微信之前）：先用 `shell()` 读 `settings get system screen_off_timeout`
  记下原始值并校验是非空数字，校验不过就停下；再用 `settings put system screen_off_timeout 1800000`
  改成 30 分钟，改完必须读回确认确实是 1800000，读回不对时写明警告并继续（此前任务在 10 分钟超时下
  也曾跑通，改不成就不能因此直接判失败），但要在汇报里写明屏幕仍可能在原始超时后变暗。
  30 分钟是有限值，不是“永不灭屏”；不要用 0、-1 或极大值去凑常亮，也不要用定时点屏幕来保活，
  点按很可能误点到微信界面里，比灭屏更危险。充电才常亮的路也不用，手机不一定在充电，改超时才跟充电状态无关。
- 结束时（第 6 步，恢复输入法之后、删锁和发“已完成”之前）：把屏幕超时改回第 1 步记下的原始值，
  再读回确认确实等于原始值；读回不对时，即使消息已发出、输入法已恢复，也要汇报为
  “消息已发、屏幕超时未恢复”，不准发“已完成”通知。
- 主动停下时同样要尝试改回原始值并读回确认，改不回去时如实写“无法恢复”，不要编一个值。
  被杀、超时导致 Hermes 发不出恢复时，调用方按“中断后调用方核对清单”里的原始值去恢复，
  所以调用方开跑前预检里也要先记一份原始值，不能只靠 Hermes 任务内的记录。
- 红线：任务开始时屏幕已经灭了、锁了，就停下交回用户，不要发唤醒、滑动、解锁去硬拉回来。
  常亮逻辑只负责“执行期间不灭”，不负责“把锁屏打开”；出现锁屏、密码、验证码页面时按原有规则停下。
- 未实发验证项：30 分钟值在该机型上是否能被接受并读回 1800000，下次实发时必须核对，读回不对时
  按本节的警告路径处理，不要默认它已生效。

## v1.3.3 改动（2026-10-26，任务状态文件与确定性看门狗，未实发验证）

背景：2026-10-26 high 对比一趟在核对会话标题阶段空转约 14 分钟才被人工中断，
服务器日志因单次运行输出缓冲到结束才落盘而是 0 字节，事后无法从日志知道它在等什么。
本节只加状态上报和硬上限，不动主流程、不引新工具、不加 LLM 宏观调控（那是以后的一档）。

- 新增手机状态文件：每步动手前和动手后，都用手机上的 `shell()` 往手机里追加一行状态，
  路径为 `/sdcard/Download/hermes-task-status.jsonl`，一行一个 JSON，只写通用字段，不写消息内容、
  不写联系人名、不写截图路径。字段为：`ts`（手机时间戳，秒）、`run_id`、`stage`（阶段名，例如
  “核对会话标题”、“输入消息”、“发送”）、`action`（本步动作，例如 “screen”、“ui”、“tap”、“wait”）、
  `attempt`（本阶段第几次读屏或尝试，从 1 开始）、`target_count`（文字逐字等于目标的气泡数，无则写 -1）、
  `total_count`（全部已发出气泡数，无则写 -1）、`error`（空字符串或简短错误码，例如 “title_not_found”）。
  第 1 步写锁之后、打开微信之前，先写一行 `stage` 为“开始”的状态；正常结束和主动停下时，最后写一行
  `stage` 为“已完成”或“任务中断”的状态，再删锁。状态行本身就是心跳：看门狗按最后一条状态行的时间判卡住。
- 新增标题核对硬上限：进会话后核对标题时，读屏次数最多 3 次（`attempt` 为 1、2、3），
  3 次都认不出逐字标题就主动停下，按“主动停下时的收尾”恢复输入法、恢复屏幕超时、删锁、发“任务中断”通知，
  再汇报“标题核对 3 次未通过”。不要把“没认出来”理解成“还没加载出来”无限等下去；
  读屏之间只用 `wait_stable()`，不要用固定长等待硬拖。标题被通知横幅遮挡时，第一次读屏未通过要先等
  横幅消失再读第二次，仍计入 3 次上限，不另开上限。
- 新增标题核对前的前台关卡：读标题之前，先用 `shell()` 跑 dumpsys 看当前应用包名，
  包名不是微信时直接停下，不要在别的 App 的屏幕上等标题；前台关卡失败同样按主动停下收尾，
  并在状态行里写 `error` 为 “foreground_not_wechat”。
- 调用方看门狗协议（见“任务状态文件与看门狗”一节）：调用方在启动 Hermes 之前，先在服务器上写
  看门狗监视文件，含 run-id、模型、开始时间、超时秒数、原始输入法、原始屏幕超时；看门狗每分钟读一次
  手机状态文件并生成服务器状态 md，卡住时停任务并恢复。Hermes 任务内不需要读服务器文件，
  状态上报只走手机文件这一条路，因为 `shell()` 跑在手机上，写不到服务器文件里。

## v1.3.4 改动（2026-10-26，对抗审查后修关键项，看门狗 v1.1，未实发验证）

- 状态行定死写法：以前只写了字段名，没给手机上那条 shell 命令怎么写，模型自由拼 JSON 时，
  引号、美元符、反引号会把 shell 命令拼坏，看门狗解析时直接跳过坏行，心跳就断了。
  从 v1.3.4 起，状态行必须按下面模板写，字段里不准出现单引号、双引号、美元符、反引号、换行，
  出现时先替换成下划线再写；`ts` 必须是秒级整数，不是毫秒。模板里的 RUN_ID、STAGE 等是占位符，
  写的时候替换成实际值，不要原样照抄：
  ```python
  # step: 写状态行（动手前和动手后各写一次；首行用 > 截断，之后各行用 >> 追加）
  shell("printf '%s\\n' '{\"ts\":TS,\"run_id\":\"RUN_ID\",\"stage\":\"STAGE\",\"action\":\"ACTION\",\"attempt\":N,\"target_count\":T,\"total_count\":C,\"error\":\"ERR\"}' > /sdcard/Download/hermes-task-status.jsonl")
  shell("printf '%s\\n' '{\"ts\":TS,\"run_id\":\"RUN_ID\",\"stage\":\"STAGE\",\"action\":\"ACTION\",\"attempt\":N,\"target_count\":T,\"total_count\":C,\"error\":\"ERR\"}' >> /sdcard/Download/hermes-task-status.jsonl")
  ```
  其中 `TS` 先用 `shell("date +%s")` 读回再填，不要自己估时间；首行用 `>` 截断旧文件，
  之后各行一律用 `>>` 追加，跨任务的文件增长问题就从源头截断了，不靠事后清理。
- run-id 不得复用：每次尝试都要用新的 run-id，哪怕上一次是参数报错、根本没跑起来，
  也不准用同一个 run-id 重跑；看门狗再按开始时间过滤一层旧行，两层防线缺一不可。
- 监视文件写在启动时：调用方写监视文件的时机是“紧贴着启动 Hermes 之前”，不是“基线核对之前”，
  `started_epoch` 就是 Hermes 启动时间；基线核对花的时间不算进任务总时长，否则看门狗会提前误杀。

  screen() 返回失败或空结果时，仍要写 screen_end 行（error 写简短错误码），再写 check_title_after 判不过，
  不要跳过 screen_end 直接判标题，否则 screen 步骤会变成未配对的单行，耗时算不出来。
- 看门狗步骤级统计（v1.7）：_before / _begin 行打开一步，_after / _end 行关闭同一阶段、同一基名的已打开步骤，
  步骤可以嵌套（check_title 对里夹着 screen 对），单行步骤耗时为 0 秒，不表示失败；
  md 里新增“各步骤耗时”一节，--stage-stats 也同时出阶段表和步骤表。
  这样下一趟不仅能看到标题阶段 172 秒，还能看到 screen 步骤和 check_title 步骤各自是多少，输入的四个子步骤也能各自看到，
  不再被一个阶段总数盖住。杀人规则、阈值、阶段与错误码白名单一律不动，步骤统计只用于事后分析，不参与卡住判定。

## 适用场景

- 用户说“用 phone_exec 给微信文件传输助手发一条消息”，且是自测。
- 给真人、真群发消息时，见“真人收件”一节，缺确认就停下。
- 不适用：密码、验证码、支付、购买、删消息、改设置、给真人发敏感内容——这些一律不做，
  出现密码或验证码输入框就停下，把手机交回用户。
- 不适用（未证实就停下）：长句、多段、表情、中英混写、数字和符号较多的内容，除非调用方已给出分段拼音方案且每段都能按下面规则核对；
  拼音首选不是目标词时也停下，不要猜点别的候选词。

## 前置条件（开始前先确认，缺一个就先停下）

- 任务提示里必须有三样东西：目标会话名、完整消息内容、运行标识（run-id）。缺 run-id 就不要开始，因为通知和锁都靠它区分新旧。
- `phone_exec` 在新会话里可用（插件启用后，工具只在新会话出现，旧会话看不到）。
- Android 设备已连通：`ensure_device()` 能返回可用状态；不要假设设备在线。
- 不要开分类器自动运行（`classifier_auto_run` 保持关闭，可绕过，不可依赖）。
- 交互会话里每次 `phone_exec` 调用都会弹窗审批；单次运行（`hermes -z`）会按设计自动跳过审批，
  用单次运行做测试时，要在汇报里写明这一点。
- 调用方超时建议设 1200 秒，不要设 600 秒——一趟完整任务接近 10 分钟量级，600 秒太紧。
  超时本身不是 skill 能保证的，skill 只规定超时后状态未知、默认停下，见“超时与中断”。

## 调用方开跑前预检（Hermes 任务开始前，调用方必做，不在任务内补做）

- adb 在线、转发监听在（服务器本机 127.0.0.1:18091 在监听，监听不在时按“转发已死”汇报，
  不要按“手机无线调试未开”汇报）、隧道在、默认模型未被改动、单例锁文件不存在，
  这几项先查，缺一就先停下；启动新一趟前还要过锁三重门：手机锁不存在、服务器上无旧 run-id 进程、
  监视文件不是 active，服务器侧先跑 `task_watch.py --check-launch --previous-run-id <旧 run-id>` 过关再写新监视文件。
- 查残留任务时注意自匹配陷阱：直接用进程名查 Hermes 时，查命令本身的进程也可能被算进去，
  单独一个匹配数不能证明有残留任务，必须排除查命令自己的进程后再下结论。
- 查输入法读回值：若已是临时用的微信输入法且无正在跑的任务、无单例锁，按 v1.3.1 的残留判定先恢复回
  用户正常输入法并读回确认，再开跑；不要把残留值当成原始值。
- 查会话列表草稿：目标行带草稿标记时，在进会话之前就停下并汇报，等用户清掉草稿或在新的一轮里
  明确授权处理这条草稿；用户说已清掉后，调用方必须自己再核对一次，不能只信口头说法。
  前台不是微信时不要为了查草稿和基线去导航打扰用户正在用的手机，基线没查到时监视文件里如实写
  baseline_checked_by_caller 为 false，不要谎称已核对。
- 记两份原始值：预检时记一次输入法与屏幕超时，紧贴启动前再记一次，两次不一致时以启动前那次为准
  写进监视文件，并在启动汇报里写明不一致；屏幕超时原始值（2026-10-26 实测为 600000 毫秒）供 Hermes 被杀、
  超时后调用方恢复用；Hermes 任务内第 1 步还会再记一次，三份值对不上时以调用方启动前的值为准并在汇报里写明。
- 核对截图必须确实是微信前台：截图若显示的是别的 App（例如聊天 App 本身），那张图不能证明草稿已清、
  不能证明气泡基数，必须重新回到微信再截一次；前台不是微信时，不要用那张图下任何结论。

## 任务状态文件与看门狗（v1.3.3 起，确定性一档，不含 LLM 调控）

- 手机状态文件：`/sdcard/Download/hermes-task-status.jsonl`，Hermes 每步动手前和动手后各追加一行，
  字段见 v1.3.3 一节。状态行不写消息内容、不写联系人名、不写截图路径，只写阶段、动作、尝试次数、
  底部窗口计数、简短错误码。看门狗不读微信聊天内容，只读这个文件和系统状态（adb 在线、前台应用、
  输入法读回值、屏幕超时读回值、锁是否存在），不读屏、不点按微信。
- 服务器监视文件：调用方在紧贴着启动 Hermes 之前写 `/root/life/task_watch.json`，内容只含：
  `run_id`（每次尝试都用新的，不复用）、`model`、`task`（通用任务名，例如“文件传输助手发你好（自测）”，
  不写消息内容）、`started_epoch`（Hermes 启动时间戳，秒，不是基线核对开始时间）、`timeout_seconds`（1200）、
  `original_ime`、`original_timeout`、`active`（true）。任务正常结束或被看门狗停掉后，看门狗把 `active` 改成 false，
  监视文件留作审计，不删除；下一次任务由调用方写新的监视文件覆盖。
- 服务器状态 md：看门狗每分钟生成 `/root/life/task_status.md`，先写临时文件再改名覆盖，
  内容只含：run-id、模型、开始时间、已用时间、当前阶段、本阶段已持续时间、最后心跳时间、
  底部窗口基数、状态（运行中 / 已完成 / 已中断 / 卡住已停）、中断原因、锁是否存在、输入法与屏幕超时
  是否已恢复，以及 v1.6 起的“各阶段耗时”一节（每阶段起止、阶段内耗时、行数、阶段间间隔、启动间隔）
  和 v1.7 起的“各步骤耗时”一节（每步起止、步骤内耗时、行数、步骤间间隔，screen 步骤与 check_title 步骤分开列）。
  无进行中任务时，看门狗不改写状态 md，md 保持上一次任务的最终状态。
  事后分析用 `task_watch.py --stage-stats` 只读出阶段表和步骤表，不写 md、不改监视、不杀进程。
- 看门狗脚本：服务器 `/root/life/task_watch.py`（v1.7），cron 每分钟跑一次，单例锁拿不到就直接退出，
  不并行跑；无监视任务时静默退出，不发通知、不改手机状态。卡住判定（任一成立即停，阶段为“已完成”
  或“任务中断”时不判）：总时长超过监视文件里的超时秒数；服务器最后一次看到新状态行超过 300 秒；
  核对会话标题阶段的读屏次数达到 4 次（只数 _before 行，即 Hermes 本应 3 次就停而没停时，看门狗兜底）；
  同一阶段按服务器观测时间超过 900 秒；连续两次检查前台都不是微信（仅在已有状态行且阶段超出“开始”后计数，
  启动阶段不算、不杀）；
  adb 连续两次查不到设备且心跳已超过 300 秒。无原因、无进程、无状态行时只写“等待首条状态”，
  不停任务、不改监视；监视文件类型不对时写“监视文件无效”md 并停用监视，不静默退出。
- 看门狗停任务时的动作（按顺序，全部是确定性动作，不猜测、不发消息）：
  按 run-id 在服务器进程里找 Hermes 单次任务（shell 包装器一律排除，只杀 Hermes 本体与超时包装器），
  先 SIGTERM，等 5 秒仍在则 SIGKILL；停后重读状态文件，最后阶段已到发送或收尾、或最后动作为 send_after 时，
  md 里写明点发送可能已发生，禁止按未发出重发；状态行只认白名单阶段与错误码，其他一律过滤进不了 md；
  dashboard、gateway 等不含该 run-id 的 Hermes 进程一律不动；若 adb 在线，恢复输入法回原始值并读回确认、
  恢复屏幕超时回原始值并读回确认、发一条 `阶段：任务中断 [run RUN_ID]` 通知（按参数列表传，不用字符串切分）；
  再重新读一次锁、前台、输入法、超时写进 md 做停后核对，并写明看门狗无法核对气泡、停后是否已发出须调用方截图核对；
  更新状态 md 为已中断并写明原因；把监视文件 `active` 改成 false。**锁不删**：残留锁按 fail-closed 留给用户
  在确认手机安全后手动删，看门狗只在状态 md 里写明锁仍存在；下一趟因锁存在而停下是预期行为，不是看门狗故障。
- 看门狗发现 Hermes 进程已不在、且最后阶段不是终态时，同样按上条做恢复和状态更新（进程已死就不再杀），
  不要因为进程已死就默认任务成功。发现最后阶段已是“已完成”时，只做一次恢复核对（输入法、屏幕超时
  与原始值不符时改回去并在 md 里写明），再把监视文件 `active` 改成 false。
- 未来 LLM 宏观调控的预留：本档不实现控制文件回路，只预留状态 md 和监视文件这两个接口；
  以后加 LLM 调控时，LLM 只读状态 md、只写控制文件，不调 phone_exec、不直接删锁，控制回路另起一节写死，
  不要把控制逻辑塞进看门狗脚本里。

## 单例与运行标识

- 开始前先用 `shell()` 查锁文件是否存在。锁文件示例路径为手机上的
  `/sdcard/Download/hermes-phone-task.lock`，内容只写 run-id，不写消息内容和会话名。
  锁存在：立刻停下，不要动微信，不要发通知覆盖别人的阶段，不要删别人的锁。
  锁不存在：先写锁，再做第一步；正常结束和主动停下时都要删锁，并发“已完成”或“任务中断”通知。
- 锁路径已于 2026-10-26 v1.3 retest（run-id 20261026-0953）实发验证通过：写锁、删锁均走通，
  调用方事后核对锁已不存在。被杀、超时导致锁残留时，下一趟会因为锁存在而停下——
  这是故意 fail-closed，残留锁只能由用户在确认手机状态安全后手动删，不能由下一趟模型顺手删掉。
- 阶段通知正文里必须带 run-id，例如 `阶段：发送 [run 20261026-1200]`，不要只写阶段名。
  旧通知和新通知阶段名完全一样时，run-id 是唯一能区分新旧的办法。

## 阶段通知（通知栏提示，2026-10-25 实测加入）

任务进行中，让用户下拉通知栏就能看到当前到哪一步，不用切进聊天看进度。
每步开头先发一次阶段通知，再做该步的操作；同一个标签反复发就是更新同一条通知，不会刷屏。
标题核对步骤除外：先读屏、后发通知，不要先发通知再读标题；自家阶段通知的横幅遮挡时，
等横幅消失再读的那一次不计入 3 次上限，微信或其他 App 的横幅遮挡时仍计入。

```python
# task: 给微信文件传输助手发一条你好
# step: 发阶段通知（先发通知，再做本步操作）
shell('cmd notification post -t "Hermes 手机任务" hermes-phone-task "阶段：核对会话标题 [run RUN_ID]"')
```

- 标题固定为 `Hermes 手机任务`，标签固定为 `hermes-phone-task`，正文只写阶段和 run-id，不写消息内容、
  不写对方名字——通知栏在锁屏也可能可见，阶段文字越通用越好，例如：
  `阶段：打开微信` / `阶段：核对会话标题` / `阶段：输入消息` / `阶段：发送` / `阶段：恢复输入法`。
- 任务正常结束时，最后发一条 `阶段：已完成 [run RUN_ID]`，再汇报。顺序必须是：气泡基数核对通过、输入法恢复并读回确认、
  屏幕超时恢复回原始值并读回确认、删锁、发“已完成”、再汇报；任一恢复没通过时不准发“已完成”。
- 任务中途失败或主动停下时，最后发一条 `阶段：任务中断 [run RUN_ID]`，再汇报，不要让通知栏一直停在旧的“进行中”阶段。
  被杀、超时时模型发不出这条通知，调用方必须按“中断后调用方核对清单”处理，不能默认通知状态就是任务状态。
- 已知限制（Android 16 实测）：系统命令只有发、没有删，这条通知要用户自己在通知栏划掉；
  不要为了“删通知”去试没有验证过的系统调用。通知本身不发消息、不点按、不改设置，只是提示。

## 定位混合规则：先结构、后截图（v1.3 起为硬性规则）

定位、找输入框、找发送按钮这三处，统一按下面顺序做，不要只信结构，也不要只信截图：

1. 同一屏状态下，先调一次 `ui()`。`ui()` 就是 adb 的 uiautomator dump，返回节点时每个节点带类名、
   resource-id、文字、描述、屏幕范围、是否可点。
2. 节点非空且目标节点在里面（文字逐字等于目标、或 resource-id 对得上、且可点）时，用该节点的屏幕范围中心点按、
   用该节点的文字和状态做核对；不要再用截图估一个坐标去点同一个东西。
3. 节点为空、目标不在节点里、或节点范围明显不对时，立刻切到 `screen()` 文字框加截图：
   用文字框的中心点按，用截图核对标题、输入框、发送按钮。切过去就不要再回头重试 dump。
4. 同一屏上最多调一次 `ui()`。滚屏、点按、`wait_stable()` 之后屏幕已变，才可以为新屏再调一次；
   在同一屏上反复调 dump 不会让空树变满，只会浪费时间——微信实测就是单空节点，反复试也没有用。
5. 结构和截图冲突时，以更严格的那个为准停下：例如结构里标题对、截图里标题不对，或反过来，
   都按“核对不过”处理，停下汇报，不要挑一个对自己有利的结果继续。
6. 微信会话内 ui() 空树只确认一次（v1.3.10 起，A2）：本趟内第一次进目标会话时调一次 `ui()` 确认是空树，
   确认之后本会话内剩余步骤直接走 `screen()`，不再每步重调 `ui()`；回到会话列表、换会话、换 App、
   或 `screen()` 找不到目标时，重新调一次 `ui()` 确认。以下各处“先看 `ui()`”一律以本条为准。

## dumpsys 辅助核对（只能辅助，不能当依据）

- 用 phone_exec 的 `shell()` 跑 `dumpsys activity activities` 和 `dumpsys window windows`，
  看当前应用包名和焦点窗口，确认当前是不是微信、是不是在微信界面里。
  包名对不上微信时立刻停下，不要继续点按——这能防住“别的 App 里出现同名文字”的情况。
  管道里的 `grep` 无匹配会返回非零退出码，命令里必须加 `|| true` 兜底，不要把 grep 无匹配当成任务失败。
  Linux 端不要调 `screen_info()`，它会报 Quartz 模块缺失，直接用 `screenshot()` 配合视觉核对。
- dumpsys 的限度必须写死在执行里：它给不了会话行、输入框、发送按钮的精确坐标，
  不能用它的输出去算点按坐标；它的活动名只能证明进了微信，不能证明进了哪一个会话，
  会话身份仍以顶部标题逐字核对为准，dumpsys 永远不能代替标题关卡。
- dumpsys 查不到、输出看不懂时，不要把它当成通过，也不要把它当成失败的唯一证据：
  以标题关卡为准继续或停下，并在汇报里写明 dumpsys 未能确认，不要编一个 dumpsys 结论。

## 黄金流程（按这个顺序，每步只做一件事，做完立刻核对）

把下面步骤各写成一个 `phone_exec` 脚本，不要把“打开、输入、发送”全塞进一个脚本里赌运气，
也不要一个点按发一次调用。已验证的序列可以成组，但每组末尾必须留一个便宜的核对。
每步脚本开头先按上一节发一次阶段通知（带 run-id）。

1. **单例、常亮与登录态**
   - 先查锁（见“单例与运行标识”），锁存在就停下；锁不存在就写锁。
   - 写锁后先写一行手机状态文件，`stage` 为“开始”，再往下走；此后每步动手前和动手后都按
     “任务状态文件与看门狗”一节追加状态行，状态行不写消息内容和联系人名。
   - 再做临时常亮：读 `settings get system screen_off_timeout` 记原始值并校验是非空数字，校验不过就停下；
     用 `settings put system screen_off_timeout 1800000` 改成 30 分钟，读回确认确实是 1800000，
     读回不对时写明警告并继续，不要因此判失败；任务开始时屏幕已灭、已锁时停下交回用户，
     不要唤醒、滑动、解锁。常亮只防执行期间灭屏，不负责打开锁屏。
   - `ensure_device()`，然后打开微信。中文别名 `open_app("微信")` 若未命中，改用包名 `com.tencent.mm` 再试一次，
     两次都失败就停下，不要反复点。别名未命中是已知情况（2026-10-26 retest 再次出现），改包名成功不算报错重试，
     但要在汇报里写明走了这条 fallback。
   - 打开微信后只等一次稳定（v1.3.10 起，A4），然后读屏：若出现登录、二维码、密码、验证码页面，立刻停下，
     把手机交回用户，不要输入任何凭据。读屏和下面 dumpsys 共用这次稳定结果，不再为 dumpsys 单独等第二次。
   - 用 `shell()` 跑 dumpsys 做辅助核对：当前应用包名对不上微信时停下；
     dumpsys 只能辅助，不能代替下面第 3 步的标题关卡，也不能用来算点按坐标。
   - 若当前屏不是会话列表也不是目标会话，先看清它是什么：若是某个非目标会话且其输入框非空，**整趟停下**，
     不要按返回、不要导航、不要动那个输入框——那很可能是用户自己的草稿，导航本身也可能干扰用户正在用的手机。

2. **打开并定位（最多找两次，翻屏最多三屏）**
   - 按“先结构、后截图”找目标会话：先调一次 `ui()`，节点里有文字逐字等于目标的可点行时，点该节点范围的中心；
     节点为空或目标不在节点里时，立刻切到 `screen()` 文字框加截图，用文字框的中心点按，不要在同一屏上反复调 dump。
     注意：用 `open_app` 回到微信时，经常直接回到上次打开的会话，而不是会话列表——
     **不要假设当前是列表，先读屏，看清当前到底是列表还是某个会话**。
   - 若当前确实是会话列表，先看目标行有没有草稿标记（例如“[草稿]”）：有标记时在进会话之前就停下汇报，
     不要点进去再确认；若当前已经直接回到了目标会话，则按第 3 步的输入框检查处理，同样是非空就停下。
   - 点会话行时点**行中心**（节点范围中心或文字框中心），不要点行边缘。第一次实测就是点了行边缘，结果打开了另一个联系人的会话。
   - 如果目标不在当前屏，用 `scroll()` 慢慢找，翻屏超过三屏还没找到就停下，不要凭记忆点位置。
   - 定位尝试计数写死：一次定位尝试 = 进一次会话列表、找目标直到找到、或翻屏满三屏、或标题不符退出为止；
     置顶折叠在一个尝试内只点一次展开，展开后重读屏，不另算一次尝试；不要用微信搜索框找目标会话。
   - 定位失败累计两次（标题不符退出算一次）就整趟停下，不要无限循环开错会话。
   - 定位阶段只读会话列表的标题行，不要把非目标会话的聊天内容读进上下文；标题不对时立刻退出，不要继续读屏。

3. **标题关卡与进入时核对（硬性停止点）**
   - 进会话前先过前台关卡：用 `shell()` 跑 dumpsys 看当前应用包名，包名不是微信时直接停下，
     不要在别的 App 的屏幕上等标题；前台关卡失败时在状态行里写 `error` 为 “foreground_not_wechat”。
   - 进会话后立刻 `screen()`，核对顶部居中标题**逐字等于**目标会话名（例如“文件传输助手”），
     每次读屏都在状态行里写 `attempt`（1、2、3）。**读屏最多 3 次**：3 次都认不出逐字标题就主动停下，
     按“主动停下时的收尾”恢复输入法、恢复屏幕超时、删锁、发“任务中断”通知，再汇报“标题核对 3 次未通过”；
     不要把“没认出来”理解成“还没加载出来”无限等下去。标题被通知横幅遮挡时，先等横幅消失再读第二次，
     仍计入 3 次上限。
   - 标题不对：立刻 `back()` 退出，**不要在该会话里输入、发送任何东西**，按第 2 步的次数限制重新定位或停下。
   - 标题对了，dumpsys 只能再辅助确认一次当前是微信，不能代替标题；标题和 dumpsys 冲突时按核对不过停下。
   - 标题、输入框空、底部窗口锚点三项同屏一次读屏核对（v1.3.10 起，A1），缺一不可，状态行和汇报里三项分开写、分开判：
     - 写行顺序：先写一行 stage 为“核对会话标题”、action 为 check_title_before 的状态行，
       再写一行 stage 为“核对会话标题”、action 为 screen_begin 的状态行，然后只读一次屏，
       再写一行 stage 为“核对会话标题”、action 为 screen_end 的状态行，再写标题 after 行、输入框空核对行，
       然后写记基数 before 行和 after 行；
       记基数 before / after 之间不准再读第二次屏，这两行夹的是“用同屏结果解释底部锚点”这一步，不是第二次读屏。
       标题 after 行的 action 为 check_title_after，标题仍须逐字等于目标会话名，不对就按上面标题不对的规则停下。
       screen_begin / screen_end 是测量行（v1.3.11 起），故意不带 _before 后缀，不计入标题读屏次数；
       绝对不准写成 screen_before，否则每屏标题计数会虚增，见 v1.3.11 一节。每次标题尝试都要各写一套 screen_begin / screen_end 行。
     - 输入框必须为空，核对行用 stage“核对会话标题”、action“input_empty_check”（不带 _before 后缀，
       不计入标题读屏次数）。输入框非空时，无论里面是不是目标文字、哪怕只是目标的一个字前缀，都停下，
       不清空、不补打剩余部分、不发送、原样汇报；清空会毁用户草稿，补打或发送会把来源不明的文字发出去。
       会话是直接恢复进来的、键盘已经打开时，也要先按这条核对，不要因为键盘已开就默认输入框是空的。
     - 记底部窗口锚点（v1.3.8 起，不做全量计数）：只看底部，记下发送前最底部已发出气泡的时间
       （只记时间，不记内容），以及它上面一个气泡是否在同一屏可见；不要滚到顶部，不要数历史，
       不要滚到发送前底部锚点之上。发送后核对就以这个锚点为准：底部窗口里从锚点到当前底部之间
       恰好只有一条新目标消息、没有其他新已发出气泡，且最底部目标消息的时间在发送之后、晚于锚点时间。
       底部窗口找不到锚点时，核对不通过，按未知处理，绝不重发。记基数 after 行的 action 为 record_baseline_after，
       target_count / total_count 均为底部窗口计数，发送前均为 0。
     - 三项里任何一项不对，都按各自的停下规则停下，不准把另外两项写成通过；三项都对了才算进入时核对通过。
   - 标题相等只能证明进了“一个叫这个名字的会话”，不能证明是同一个人、同个群。真人收件时标题关卡不算身份确认，
     见“真人收件”。

4. **中文输入（不要绕弯路，直接走已验证的路；子步骤各写一行状态行，v1.3.10 起，A3）**
   - 本阶段 stage 一律为“输入消息”，attempt 一律为输入尝试次数（第一次尝试全为 1），子步骤用 action 区分，
     每个子步骤动手前和动手后各写一行状态行，不要等整个输入做完才写一对行。
   - 子步骤一，切输入法（action switch_ime_before / switch_ime_after）：先用 `shell()` 记下原始输入法：
     `settings get secure default_input_method`，并校验它非空且形如“包名/组件名”，
     校验不过就停下，不要在没有原始值的情况下切输入法——否则收尾无法恢复。
     临时切到微信输入法：`shell("ime set com.tencent.wetype/.plugin.hld.WxHldService")`，切完必须读回设置确认已是微信输入法，
     读回不对就停下，不要在原输入法下输拼音。
   - 子步骤二，点输入框获焦点（action focus_before / focus_after）：点输入框获得焦点后，先确认焦点确实在目标会话的输入框
     （不是搜索框、不是标题栏），再往下走。找输入框按混合规则加 A2：本会话内 ui() 空树已确认时直接用 `screen()` 的输入框文字框
     和截图定位，不要每步重调 `ui()`；节点非空且有可编辑输入框节点时才用节点范围点按，不要用旧屏的坐标。
   - 子步骤三，输拼音加空格（action type_before / type_after）：只输入拼音字母（ASCII，例如 `nihao`），
     **不要直接输中文字符**。按空格确认首选候选词之前，先确认候选词条可见；如果首选不是目标词，停下，
     不要猜点别的候选词，不要用退格反复试；停下前不要清空输入框，按“主动停下”流程恢复输入法、删锁、
     发“任务中断”通知并汇报当前输入框状态。
   - 子步骤四，读回核对（action readback_before / readback_after）：空格之后必须读屏核对输入框，确认两点：
     输入框内容逐字等于目标消息，且没有多余空格或拼音残留。读回不对时停下，不要点发送，不要清空后重输一遍去“纠正”。

5. **发送（恰好一次，点之前再核对一次）**
   - 点发送前，在同一屏再读一次：顶部标题仍逐字等于目标会话名，输入框内容仍逐字等于目标消息，
     发送按钮可见且可用（不是灰色不可点）。三项中任何一项不对都停下，不要点发送。
   - 核对通过后，先写一行 stage 为“发送”、action 为 send_before 的状态行，再点发送；
     点完立刻写一行 action 为 send_after 的状态行，再做发送后核对。这两行是被杀后判断点发送是否已发生的唯一依据，缺一不可。
     找发送按钮也按混合规则：先看 `ui()` 里有没有发送节点，有就用节点范围和可用状态核对；
     节点为空时再用 `screen()` 和截图核对发送按钮，不要用上一屏的发送按钮坐标。
   - 核对无误后，点发送按钮一次。点完立刻 `wait_stable()`，不要连续点、不要补点。
     收尾核对直接用这次稳定结果读屏，不再为收尾单独等第二次（v1.3.10 起，A4）。
   - 成功后**不要再发第二条**，不要“补发一条确认一下”。用户说重复一次，就是总共只多一条。

6. **收尾核对与恢复（缺一项都不算成功）**
   - 先写一行 stage 为“收尾核对与恢复”、action 为 verify_before 的状态行（计数 -1/-1，表示尚未核对），再读屏一次，确认底部窗口四项：最底部是目标消息且时间在发送之后、晚于发送前底部锚点时间；
     底部窗口里从锚点到当前底部之间恰好只有一条新目标消息、没有其他新已发出气泡；
     输入框已清空；没有发送失败标志（例如红色叹号或失败文案）。
     任一项不对、时间不对、有失败标志、或找不到锚点时，一律按失败或未知汇报，不要点第二次发送去“补救”。
  - 核对完立刻写一行 action 为 verify_after 的状态行（计数为底部窗口核对结果，即目标数/已发出数），再往下恢复输入法与屏幕超时；verify_before/verify_after 成对写行（v1.3.12 起），缺 before 行的旧写法仍按单行处理，不表示失败。
   - 把输入法恢复回第 4 步记下的原始值，再用 `shell()` 读设置核对一次，确认生效；读回不对时，
     即使消息已发出，也要汇报为“消息已发、输入法未恢复”，不准发“已完成”通知。
   - 把屏幕超时恢复回第 1 步记下的原始值，再读回确认确实等于原始值；读回不对时，同样汇报为
     “消息已发、屏幕超时未恢复”，不准发“已完成”通知。
   - 写一行手机状态文件，`stage` 为“已完成”，再删锁，最后发一次阶段通知 `阶段：已完成 [run RUN_ID]`，
     再汇报（通知需用户自己划掉，见上一节）。
   - 汇报只写：run-id、目标会话名、两次标题核对结果、发送前底部锚点时间、发送后底部窗口核对结果
     （新目标消息数、新已发出气泡数，均为窗口计数，不是全量数）、
     发送的消息内容、新消息的时间、输入法已恢复、屏幕超时原始值与恢复后读回值、走过的已知 fallback
     （别名改包名、grep 兜底、截图代替 screen_info、常亮读回警告时写明）。
     不要在汇报里复述屏幕上看到的其他会话名、其他人的消息内容——读屏是为了定位，不是为了外传。

## 调用方提示词规范（v1.3.10 起，A5）

调用方提示词只写下面这些，不全文复述 skill 规则，详细规则只引用本 skill 文件，Hermes 自己读 skill 文件。
模板文件由调用方保管，不进公开仓库，模板里的占位符由调用方在启动前替换成实际值，不要原样照抄：

- 任务一行：给微信〈目标会话〉发一条〈目标消息〉[run RUN_ID]，按 phone-wechat-send v1.3.10 执行，看门狗 v1.6。
- 硬规则短清单一行：标题逐字核对、输入框空、底部窗口四项、只发一次、send_before / send_after、
  恢复输入法与屏幕超时、单例锁与手机状态文件路径。
- A 档短清单一行：同屏一次读屏核对标题、输入框空、底部锚点三项；标题 screen 前后写 screen_begin / screen_end 行（不带 _before，不计标题读屏）；微信会话内 ui() 空树只确认一次；
  输入子步骤 switch_ime / focus / type / readback 各写 before / after 行；只在打开微信后、点发送后、
  标题被横幅遮挡后用 wait_stable()，其他步骤不无条件等稳定。
- 不写：skill 全文、历史气泡内容、其他会话名、聊天内容、消息内容之外的任何屏幕文字。
- 提示词文件仍用通用名，不带 run-id，任务结束后由调用方删掉，见“中间文件清理”。

## 真人收件

- 默认只做文件传输助手这类自测会话。给真人、真群发消息时，任务提示里必须同时具备：收件人全名、
  完整消息内容、用户当次的明确确认（不是“以后都这样发”这类长期授权）。缺任何一项就停下。
- 真人收件时，标题关卡之后还要在点发送前把收件人和内容再对一遍任务提示原文，原文对不上就停下；
  任务提示里没写收件人时，不要用屏幕上猜到的名字补。
- 真人收件的发送后核对与自测完全相同，基数加一、输入框空、无失败标志，缺一不可。

## 超时与中断

- 模型/服务失败分支：模型或服务返回错误（503、配额、模型不存在、超时）时，写一行 error 为 provider_error 的状态行后停下，
  最多只重试一次临时性错误，绝不中途换模型、绝不改默认模型；调用方重跑前先核对默认模型仍在配置与缓存里，
  模型已弃用或无配额时不要用同一个模型重跑。
- 超时、中断后状态未知：发送那一下可能已经点了，也可能没点；模型自己的汇报可能丢了，服务器日志也可能还是空的
  （单次运行输出是缓冲到结束才落盘，写文件不等于保住汇报）。所以超时后默认是停下，不是重发。
- 超时、中断后重跑之前，必须先按“中断后调用方核对清单”查清手机状态；查不清就不要重跑。
  查清后若输入框非空，仍按第 3 步处理：停下汇报，不自动清空、不自动把框里的文字发出去；
  只有用户在新的一轮里明确授权“就发框里现有的这一条”时，才能只点发送一次，且点之前仍要做二次标题核对。
- 发送后核对一次就结束，不要反复等待和重复读屏；重复读屏不会让一次失败的发送变成功，只会增加误点风险。

## 中断后调用方核对清单（进程被杀、超时后必做，skill 文本保证不了的部分）

- 查服务器上是否还有本次 run-id 对应的 Hermes 任务在跑，有就先停掉，确认无残留后再谈重跑，不要并发跑第二趟。
- 只读查手机：当前会话标题、底部窗口锚点时间与最底部消息时间、输入框是否为空、输入法读回值、
  屏幕超时读回值、阶段通知的 run-id 与阶段；屏幕超时仍是 30 分钟时，用调用方开跑前记的原始值改回去并读回确认。
- 输入法不是原始值时，先恢复并读回确认；其中一种残留要单独认出来：当前输入法已是临时用的微信输入法、
  且无正在跑的任务、无单例锁时，就是上一趟被杀留下的残留，先恢复回用户正常输入法，不要把它当成原始值。
  会话列表目标行带草稿标记时，同样先停下，等用户清掉或明确授权处理；用户说已清掉后必须自己再核对一次，
  且核对截图必须确实是微信前台。
- 输入框非空时，不清空、不补打、不发送；有 send_after 且底部窗口核对通过时，说明上一趟已经发出，
  不要再发一条“确认”。被杀后发送状态判定一律 fail-closed：有 send_after 且底部窗口通过即按已发出处理；
  无 send_after 或底部窗口找不到锚点时按未知处理，绝不重发，
  等用户本人确认；输入框空不能单独证明未发出。
- 事后核对时比对 Hermes 汇报的原始输入法与超时与监视文件原始值，不一致时不能只凭看门狗 md 写已恢复，
  须人工确认恢复结果；提示词文件在任务结束后由调用方删掉，核对截图在汇报后删掉，除非用户明确说要留。
- 以上任何一项查不清时，整趟保持暂停，等用户本人确认，不要擅自补发或重跑。

## 主动停下时的收尾（模型还能执行时必做）

- 恢复输入法并读回确认（原始值校验不过时要如实写“无法恢复”，不要编一个值）。
- 恢复屏幕超时回原始值并读回确认，改不回去时同样如实写“无法恢复”，不要编一个值。
- 写一行手机状态文件，`stage` 为“任务中断”，`error` 写停下的原因简码，再删锁、发“任务中断”通知。
- 删锁，发 `阶段：任务中断 [run RUN_ID]` 通知。
- 汇报当前状态：标题、基数、输入框、输入法、停在哪一步、为什么停。不要在停下汇报里写“已完成”。

## 走不通的路（实测踩过，不要再试）

- **直接输中文**：`adb input text` 输中文会直接报错；`type_text` 输中文也不要假设它能行。
  拼音字母走 `input` / 按键事件时，字母是原样进输入框的，不会经过拼音联想——
  所以“先切英文模式再输拼音”是无效的，必须是中文输入法下的拼音联想。
- **搜狗中英切换反复点**：实测点了两次都没有可靠切到中文模式，白白浪费两轮。
  不要在这个键上反复试错，直接切微信输入法。
- **切百度输入法**：一切过去就会弹出首次使用的隐私同意全屏页。
  **不要点“同意并使用”**，那是替用户做的隐私授权。直接返回，恢复原始输入法，换微信输入法。
- **点候选词上屏**：实测里用 adb 点候选词两次都没有上屏。优先用空格确认首选，
  并且空格之后必须读屏核对输入框，不要假设已经上屏。
- **屏幕点按输拼音**：逐个点屏幕键盘字母时，坐标稍有偏差就会打错（实测打成了别的文字，
  当时立刻清空，没有发送）。能用按键事件 / `type_text` 输拼音字母，就不要逐键点屏幕。
- **剪贴板粘贴**：后台环境下读手机剪贴板是空的，粘贴路线走不通；而且没核对剪贴板内容就粘贴，
  有贴错旧内容进目标会话的风险。不要用这条路。
- **用界面结构树定位微信**：微信的界面结构树经常是空的，不要只依赖 `ui()`。
  以 `screen()` 的文字框和截图为准，`screen()` 的框自带可点的中心点。
- **无锁并发、超时后盲目重发、输入框非空时顺手清空或顺手发送**：以上三条在 v1.2 里都是明确禁止的，
  不要以“提高成功率”为理由绕过。

## 效率要点（为什么这样更快）

- 每个 `phone_exec` 脚本开头写清 `# task:`（用户一句话的需求，全程不变）和 `# step:`（本脚本只做哪一步），
  这是 `phone-harness` skill 的要求，也是出了问题能定位到哪一步的唯一办法。
- 用 `screen()` 的文字框定位和点按，不要每步都截图再人工估坐标；截图只在 `screen()` 看不清图标、状态时才用。
- 用 `wait_for_text` / `wait_stable` 等结果，不要用固定 `wait(n)` 硬等。
- 序列一旦验证过就可以成组，但“打开、dumpsys 辅助核对、按先结构后截图定位、核对标题、查空输入、记底部窗口锚点、输入、
  核对输入框、二次核对标题、发送、核对底部窗口四项、恢复输入法、恢复屏幕超时”这些核对点一个都不能省——省掉核对省下的时间，
  远不够一次发错会话的代价。调用方开跑前预检（adb、模型、输入法残留、锁、会话列表草稿、前台截图）同样不能省，
  它是 Hermes 任务内无法补做的部分。

# 按先结构后截图定位：先调一次 ui()，节点里有目标行就点节点范围中心，节点为空就切 screen() 文字框加截图，不要同一屏反复 dump
