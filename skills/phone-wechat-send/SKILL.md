# 用 phone_exec 给微信发消息

本 skill 建立在 `phone-harness` skill 之上：helper 名称、调用方式、审批规则以那个 skill 为准。
本 skill 只补一层东西：**在真实微信里发中文消息时，哪些路走不通、哪条路一次就能走通、以及在哪个关卡必须停下来核对**。

## 适用场景

- 用户说“用 phone_exec 给微信某人 / 某群 / 文件传输助手发一条消息”。
- 尤其适用：消息是中文；目标是文件传输助手这类“自己给自己发”的会话。
- 不适用：密码、验证码、支付、购买、删消息、改设置、给真人发敏感内容——这些一律不做，
  出现密码或验证码输入框就停下，把手机交回用户。

## 前置条件（开始前先确认，缺一个就先停下）

- `phone_exec` 在新会话里可用（插件启用后，工具只在新会话出现，旧会话看不到）。
- Android 设备已连通：`ensure_device()` 能返回可用状态；不要假设设备在线。
- 记录原始输入法，结束时必须恢复（见“收尾”）。
- 不要开分类器自动运行（`classifier_auto_run` 保持关闭，可绕过，不可依赖）。
- 交互会话里每次 `phone_exec` 调用都会弹窗审批；单次运行（`hermes -z`）会按设计自动跳过审批，
  用单次运行做测试时，要在汇报里写明这一点。

## 阶段通知（通知栏提示）

每步开头先发一次阶段通知，再做该步的操作；同一个标签反复发就是更新同一条通知，不会刷屏。

```python
# task: 给微信文件传输助手发一条你好
# step: 发阶段通知（先发通知，再做本步操作）
shell('cmd notification post -t "Hermes 手机任务" hermes-phone-task "阶段：核对会话标题"')
```

- 标题固定为 `Hermes 手机任务`，标签固定为 `hermes-phone-task`，正文只写阶段，不写消息内容、
  不写对方名字——通知栏在锁屏也可能可见，阶段文字越通用越好。
- 任务正常结束时，最后发一条 `阶段：已完成`，再汇报。
- 任务中途失败或停下时，最后发一条 `阶段：任务中断`，再汇报，不要让通知栏一直停在旧的“进行中”阶段。
- 已知限制（Android 16 实测）：系统命令只有发、没有删，这条通知要用户自己在通知栏划掉；
  不要为了“删通知”去试没有验证过的系统调用。通知本身不发消息、不点按、不改设置，只是提示。

## 黄金流程（按这个顺序，每步只做一件事，做完立刻核对）

把下面 5 步各写成一个 `phone_exec` 脚本，不要把“打开、输入、发送”全塞进一个脚本里赌运气，
也不要一个点按发一次调用。已验证的序列可以成组，但每组末尾必须留一个便宜的核对。
每步脚本开头先按上一节发一次阶段通知。

1. **打开并定位**
   - `ensure_device()`，然后 `open_app("微信")`，`wait_stable()`。
   - `screen()` 读屏找目标会话。注意：用 `open_app` 回到微信时，经常直接回到上次打开的会话，
     而不是会话列表——**不要假设当前是列表，先读屏，看清当前到底是列表还是某个会话**。
   - 点会话行时点**行中心**，不要点行边缘。点行边缘曾经打开过另一个联系人的会话。
   - 如果目标不在当前屏，用 `scroll()` 慢慢找，不要凭记忆点位置。

2. **标题关卡（硬性停止点）**
   - 进会话后立刻 `screen()`，核对顶部居中标题**逐字等于**目标会话名（例如“文件传输助手”）。
   - 标题不对：立刻 `back()` 退出，**不要在该会话里输入、发送任何东西**，重新定位。
   - 标题对了，才能进入下一步。这是整个流程里最重要的一道关。

3. **中文输入（不要绕弯路，直接走已验证的路）**
   - 先用 `shell()` 记下原始输入法：`settings get secure default_input_method`。
   - 临时切到微信输入法：`shell("ime set com.tencent.wetype/.plugin.hld.WxHldService")`。
   - 在输入框获得焦点后，只输入拼音字母（ASCII，例如 `nihao`），**不要直接输中文字符**。
   - 按空格确认首选候选词。实测里首选就是目标词（`nihao` 的首选是“你好”）。
   - 输入框里出现目标文字后，**先读屏核对输入框内容逐字等于目标消息**，再点发送。
   - 如果首选不是目标词，停下，不要猜点别的候选词，不要用退格反复试——把当前屏的状态报给用户。

4. **发送（恰好一次）**
   - 核对无误后，点发送按钮一次。
   - 成功后**不要再发第二条**，不要“补发一条确认一下”。

5. **收尾核对与恢复**
   - 再读屏一次，确认三点：聊天底部出现一条新发出的目标消息、输入框已清空、没有多余的新消息。
   - 把输入法恢复回第 3 步记下的原始值，再用 `shell()` 读设置核对一次，确认生效。
   - 最后发一次阶段通知 `阶段：已完成`，再汇报（通知需用户自己划掉，见上一节）。
   - 汇报只写：目标会话名、标题核对结果、发送的消息内容、新消息的时间、输入法已恢复。
     不要在汇报里复述屏幕上看到的其他会话名、其他人的消息内容——读屏是为了定位，不是为了外传。

## 走不通的路（实测踩过，不要再试）

- **直接输中文**：`adb input text` 输中文会直接报错；`type_text` 输中文也不要假设它能行。
  拼音字母走 `input` / 按键事件时，字母是原样进输入框的，不会经过拼音联想——
  所以“先切英文模式再输拼音”是无效的，必须是中文输入法下的拼音联想。
- **搜狗中英切换反复点**：实测点了两次都没有可靠切到中文模式，白白浪费两轮。
  不要在这个键上反复试错，直接切微信输入法。
- **切百度输入法**：一切过去就会弹出首次使用的隐私同意全屏页。
  **不要点“同意并使用”**，那是替用户做的隐私授权。直接返回，恢复原始输入法，换微信输入法。
- **点候选词上屏**：实测里用 adb 点候选词两次都没有上屏。优先用空格确认首选，
  并且空格之后必须读屏核对输入框，不要假设已经上屏。
- **屏幕点按输拼音**：逐个点屏幕键盘字母时，坐标稍有偏差就会打错。能用按键事件 / `type_text` 输拼音字母，就不要逐键点屏幕。
- **剪贴板粘贴**：后台环境下读手机剪贴板是空的，粘贴路线走不通；而且没核对剪贴板内容就粘贴，
  有贴错旧内容进目标会话的风险。不要用这条路。
- **用界面结构树定位微信**：微信的界面结构树经常是空的，不要只依赖 `ui()`。
  以 `screen()` 的文字框和截图为准，`screen()` 的框自带可点的中心点。

## 超时与中断

- Hermes 跑一趟微信发消息接近 10 分钟量级，单次运行超时建议设 1200 秒，不要设 600 秒。
- 超时、中断后重跑之前，必须先读屏查输入框：如果输入框里已经有目标文字，不要再输、不要清空，
  只核对、只点一次发送；否则会把目标文字打两遍再发出去。
- 发送后核对一次就结束，不要反复等待和重复读屏。

## 效率要点（为什么这样更快）

- 每个 `phone_exec` 脚本开头写清 `# task:`（用户一句话的需求，全程不变）和 `# step:`（本脚本只做哪一步），
  这是 `phone-harness` skill 的要求，也是出了问题能定位到哪一步的唯一办法。
- 用 `screen()` 的文字框定位和点按，不要每步都截图再人工估坐标；截图只在 `screen()` 看不清图标、状态时才用。
- 用 `wait_for_text` / `wait_stable` 等结果，不要用固定 `wait(n)` 硬等。
- 序列一旦验证过就可以成组，但“打开、核对标题、输入、核对输入框、发送、核对已发、恢复输入法”
  这 7 个核对点一个都不能省——省掉核对省下的时间，远不够一次发错会话的代价。
