# 可靠性：通道会断，中断不等于失败

本篇是第一阶段稳定性补记，写的是公开版发布之后又验证出来的几条，
不是推测。所有地址、端口、用户名、密钥路径在这里仍然只用占位符，
不要把真实值写进来。

## 1. 隧道回来了，不等于 adb 回来了

反向隧道和 adb 转发是两层，死法不一样：

- 隧道是手机主动建到服务器的，断了之后可能自己重连回来。
- adb 转发是服务器上手动起的进程，隧道一断它就死，隧道回来它不会自己复活。

所以恢复时要按这个顺序查，不要只看隧道状态：

1. 隧道监听还在吗，隧道探活（经隧道连回手机执行一次回显）通不通。
   注意：定时检查的状态可能滞后一个检查间隔，探活结果比状态文件权威。
2. 服务器本机的转发监听还在吗。
3. `adb devices` 里手机是不是 `device`（已授权）状态。
4. 当前输入法是谁，当前屏幕是哪个会话。
5. 只有这几项都对了，才谈下一步任务。

## 2. 配对失败，不等于没通

无线调试的配对端口每次重开配对弹窗都可能变，配对码是短时有效的，
过期就用不上，这是正常的，不要把配对失败直接当成通道没通：

- 如果服务器之前已经在手机的已配对设备列表里，直接做 `adb connect` 可能就通了，
  哪怕这次的新配对没通过。
- 只有 `adb connect` 之后 `adb devices` 仍不是 `device` 状态，才需要重新走配对流程。
- 配对码只用一次，用完即废，不要记下来、不要发到公开地方；
  不需要配对时，手机上的配对弹窗可以直接取消，不用留着。

## 3. 中断不等于失败，汇报丢了不等于没做

除了 Hermes 自身超时，还有一种中断：跑任务的运行环境本身被重启杀掉。
这时会出现一种容易误判的状态：

- 执行日志可能是空的，因为输出是最后才汇总的，杀掉就丢了汇报。
- 手机上可能停在“已输入、未发送、输入法没恢复”的半成品状态，
  也可能已经发完了，只是汇报没回来。

所以中断后第一件事永远是只读核对，不是重跑：

1. 读屏：当前标题是不是目标会话。
2. 数气泡：是不是只多了预期的那一条，有没有新气泡。
3. 看输入框：是空的，还是已经有目标文字没发出去。
4. 查输入法：是不是还停在临时输入法，没恢复。

核对完再决定：输入框已有目标文字，就只核对、只点一次发送，不要重输；
什么都没发、输入框是空的，才能谈重跑；拿不准就停下问用户。
被打断的那一趟没有有效耗时结论，不能拿它和完整跑通的那一趟比快慢。

## 4. 用户正在用手机时，停下

如果打开应用后前台不是目标会话，而是一个真实会话，
并且那个会话的输入框里还有用户自己的草稿：

- 不要点任何按钮，不要发送，不要在应用里导航去目标会话。
- 不要复述那个会话里看到的其他消息和草稿内容。
- 先停下，把现状报给用户，等用户说“只核对”或“先停下”再动。

Agent 的读屏点按和用户手动操作会互相打架，省一次导航，
远不够一次动到别人草稿的代价。

## 5. 保活的上限：adb 能做的已经到顶了

分清两条线，不要把 adb 当成万能保活：

- Termux 是一个应用：Doze 白名单、待机桶这两档是 adb 能调的常用项。
  如果查出来它已经在白名单里、待机桶是豁免档，那就是最高状态了，
  不要再把它改成活跃档，那反而是从豁免降级。
  剩下的要看手机自己的设置：WiFi 睡眠时保持连接、允许后台活动和自启动、
  前台通知别划掉、唤醒锁保持，再加服务端断线告警。
- 无线调试不是一个应用，它是系统里的调试服务，不吃白名单、待机桶那套。
  它活不活看三件事：开发者选项里的开关、是不是还连在同一个 WiFi 上、
  有没有重启（重启后开关一般会复位、端口会变，要手动重开）。
  一旦它关了，adb 通道本身就没了，服务器这边发什么 adb 命令都拉不回它，
  只能等手机上手动重开。

结论：隧道掉线不能默认归因于“白名单没设”，先按第 1 节的顺序查，
区分是隧道死了、转发死了、还是调试服务本身关了。

## 6. 模型选择标准：在列表里不等于能用

- 模型出现在服务端的模型列表里，只说明它被发现了，不说明它能调用、
  更不说明它能走通一次完整的手机任务。
- 换模型之前要逐个验证：先做一次非手机短调用看返回，再做一次完整手机任务。
- 默认模型只有在挑战者完整跑通、并且在总耗时、报错、重试、
  标题和输入框核对上都可比之后，才能讨论要不要换。
- 被打断的那一趟不算数：没有完整跑通，就没有耗时结论，
  也不能据此说某个模型更快或更慢。
