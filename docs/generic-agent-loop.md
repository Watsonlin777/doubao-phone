# 通用 Agent 循环（参考模式，未实测）

> 状态：参考模式，只借结构，不改现有行为。
> 本篇不改 `skills/phone-wechat-send/` 的任何步骤、不新增任何 skill、不改变任何已验证流程。
> 它是给“以后再有新任务”准备的循环骨架，新任务真要落地，仍须像微信发消息那样单独写 skill、逐项实测，见第 8 节。
>
> 结构参考：[Roubao（肉包）](https://github.com/Turbo1123/roubao)（MIT）。
> 肉包是原生 Android App，内含 Tools + Skills 双层 agent：意图识别后走快速路径或标准 Agent 循环，
> 循环内含规划、执行、反思、记录四层（移植自 MobileAgent-v3）。
> 本仓库只借这个结构、按云端 Hermes + 手机操控改写，**没有抄肉包的代码**，肉包的 Kotlin 实现也无法直接放进本项目。

## 1. 从肉包借什么，只借什么

| 肉包里的层 | 在本项目里对应什么 | 说明 |
| --- | --- | --- |
| SkillManager 意图识别 | 任务提示词 + skill 选择 | 先判断任务属于哪个已验证 skill，还是走通用循环；判断不准就停下问人，不猜 |
| 快速路径（高置信度） | 已验证的确定性检查 | 例如标题逐字核对、输入框判空这类一步就能定性的检查，走确定性规则，不进循环推理 |
| 标准 Agent 循环 | 观察 → 规划 → 执行 → 核对 → 反思 → 记录 | 下面第 2 节的本体，是本篇的核心 |
| Manager（规划） | Hermes 按 skill 提示词做的分步规划 | 每步只定“下一步干什么”，不定“整趟全怎么做完” |
| Executor（执行） | `phone_exec` 的一次脚本调用 | 一次调用只做一小步：一次读屏、一次点按、一次输入、一次等待 |
| Reflector（反思） | 每步做完的核对 | 拿新读屏跟预期比：到了吗、对吗、变了吗；不对就停下或回退，不硬走下一步 |
| Notetaker（记录） | 阶段通知 + 任务状态文件 + 终态文档 | 给人看的阶段提示、给机器查的状态文件、给事后复盘的终态记录，三者分开 |

借的是分层和循环形状，不是肉包的具体实现：
本项目没有 App 内 VLM 直连、没有 Shizuku 控机、没有 DeepLink 委派，
操控只走云端 Hermes + `phone_exec` + adb + 反向隧道这一条路（见 `architecture.md`）。

## 2. 循环本体

```
开始：任务 + 约束（见第 6 节）+ 步数上限 + 超时上限
  ↓
观察：读当前屏（文字框优先，空了再截图定位；旧坐标一律作废）
  ↓
规划：只定下一步，不一次定全程
  ↓
执行：一次 phone_exec 调用，只做规划里的那一步
  ↓
核对：再读一次屏，确认这一步的效果是不是预期
  ↓
反思：符合预期 → 继续；不符合 → 停下、回退或问人，不硬走
  ↓
记录：阶段通知 + 状态文件各记一步
  ↓
结束条件（第 5 节）满足 → 停；否则回到“观察”
```

关键纪律，照抄微信 skill 里已经验证过的那几条：

- **先结构、后截图**：同一屏先读结构化信息，非空就用它核对；为空或目标不在，再切截图定位，不反复重试同一种读法。
- **坐标会过期**：滚屏、点按、等界面稳定之后，之前那一屏的坐标一律作废，必须重读。
- **一次只做一步**：不把“打开、输入、发送”拼进一次调用；每步的效果都要单独核对到。
- **读屏只作核对，不作身份证明**：屏上文字能证明“到了哪一屏”，不能单独证明“该对谁做不可逆操作”（见第 6 节）。

## 3. 两条路径：快速路径与标准循环

| 路径 | 什么时候走 | 底线 |
| --- | --- | --- |
| 快速路径 | 一步就能确定性定性的检查：标题相等与否、输入框空与否、某按钮在与否 | 快速不等于跳过核对：检查本身就是核对，检查失败照样停 |
| 标准循环 | 需要多步导航、等待界面变化、结果不确定的任务 | 每步都要走第 2 节的观察 → 执行 → 核对，不允许“连点三步再一起看” |

分流错了怎么办：快速路径走完发现结论不可靠（例如读屏为空、界面变了），
立刻降级到标准循环重做这一步，不沿用快速路径的结论。

## 4. 步数与超时上限

通用循环没有上限就是无底洞，必须在任务开始前定死，任务中途不放宽：

- **步数上限**：建议值由具体任务定，写进该任务的 skill，不在本篇定死数字；
  到上限还没完成就停下汇报，不自动续杯。
- **超时上限**：同理，写进 skill；本项目微信任务的实测量级是 10 分钟一趟，
  新任务不要默认照搬这个数，要按自己的实测重定。
- **等待上限**：等界面稳定、等加载完成也要有上限，到上限仍未稳定就停下，不无限等。

上限到了的汇报要说清三件事：走到了哪一步、最后一次核对看到什么、下一步本该是什么。
只说“失败了”等于没汇报。

## 5. 停止条件（满足任一即停）

- 任务完成，且最后一次核对确认了完成态。
- 步数或超时到上限。
- 连续核对失败：同一预期两次核对不上，就停，不第三次硬试。
- 出现敏感页：支付、密码、验证码、隐私同意、授权弹窗（见第 6 节）。
- 界面状态含糊：读屏为空、标题对不上、输入框来源不明、草稿非空。
- 用户中断、通道中断（隧道、转发、adb 任一断了，循环不自己续跑）。

停下之后的处理照可靠性文档的纪律：先只读核对现状，再决定补做还是重跑，
绝不凭猜测重跑一遍——对不可逆操作，重跑等于重做一次。

## 6. 不交给循环的东西（确定性关卡，永远在循环之外）

以下决定不进循环推理、不由模型自由裁量，必须是写死的规则 + 当次明确授权：

- **发送类决定**：给谁发、发什么、发不发、发几次。标题核对、只发一次、输入框非空一律停、
  发后按底部窗口核对，这些是微信 skill 里定死的关卡，通用循环不得绕过、不得放宽。
- **密码、验证码、支付、购买、转账、订阅**：出现就停，把手机交回用户手里。
- **删消息、删文件、改系统设置**：不做（临时切输入法且事后恢复除外，见微信 skill）。
- **替用户点隐私同意、授权弹窗**：不做。
- **把读屏到的他人消息外传**：不做。

一句话：循环负责“怎么走到、怎么核对”，不负责“该不该做不可逆的事”。
后者永远是规则 + 用户当次确认说了算。

## 7. 与本项目现有件的关系

| 现有件 | 在循环里扮演什么 |
| --- | --- |
| 某个任务的 skill | 循环在该任务上的具体剧本：步骤、关卡、上限、失败处理 |
| `phone_exec` | Executor 的唯一执行口，不再另开第二条操控路 |
| 阶段通知 | Notetaker 给人看的那一份：只写阶段与任务标识，不写屏上内容 |
| 任务状态文件与终态文档 | Notetaker 给机器查和给事后复盘的那一份 |
| 看门狗（通道、任务） | 在循环之外：它管“通道活着吗、任务还活着吗”，不管循环下一步该点什么 |
| 模型选择 | 循环不决定换模型；换模型前按可靠性文档逐个实测，列表里有不等于能用 |

## 8. 落地新任务前还要实测的清单（缺一不可）

本篇本身不是验证，照着它写新 skill 之前，先把下面这几项做完，
否则“通用循环”只是纸面结构：

1. 新任务的 skill 单独立项：步骤、关卡、上限、停止条件、失败处理逐项写清。
2. 先在“自己给自己”的安全会话或无害页面里跑通，再碰真人、真群、真钱、真数据。
3. 每步的核对手段逐项实测：结构化读屏行不行、截图定位准不准、坐标过期怎么处理。
4. 中文输入、输入法恢复、超时后处理，按微信 skill 的实测清单逐项重验，不默认通用。
5. 中断复盘：超时、进程被杀、汇报丢失时，只读核对现状再决定，不盲目重跑。
6. 失败模式编号入档：通道断、读屏空、核对不上、超时，每种都要有编号、有复盘、有处理，
   而不是只在循环里多试一次。

做完这 6 项，这个任务才算从“通用循环的例子”变成“本项目验证过的任务”。
做不完之前，对外只说“参考模式”，不说“已验证通用”。
