# 架构

## 角色

| 角色 | 干什么 | 不干什么 |
| --- | --- | --- |
| 你 | 说一句话、批一次、看一次结果 | 不用每步都盯着点 |
| 云服务器 | 跑 Hermes、跑 adb、持有转发 | 不存你的密码和密钥原文（见安全文档） |
| Hermes | 理解任务、按 skill 一步步调 `phone_exec` | 不直接碰手机硬件 |
| phone-harness（phone_exec） | 把 agent 的脚本翻译成读屏、点按、输入、shell | 不替你做密码、验证码、支付 |
| adb | 服务器和手机之间的调试通道 | 不是 Termux，跑不了 termux-* 命令 |
| 反向 SSH 隧道 | 手机在 NAT 后面时，让服务器能连回手机 | 隧道断了，远程控机就断了 |
| Android 真机 | 打开应用、显示界面、接受点按输入 | 不装任何本项目之外的常驻控机应用 |

## 数据怎么走

```
任务提示词
  → Hermes（云服务器）
    → phone_exec 脚本（Python，helper 预导入）
      → phone-harness（云服务器）
        → adb（云服务器本机端口）
          → SSH 转发（云服务器本机）
            → 反向隧道（手机主动建到服务器）
              → 手机 adbd（无线调试）
                → 微信等应用界面
```

回来的方向相反：截图、读屏文字、shell 输出经同一条路回到 Hermes，Hermes 再汇报给你。

## 为什么不用云手机、不用模拟器

- 云手机是租来的另一台手机，有自己的登录和号码，不是你口袋里这台。
- 模拟器没有你的微信登录、没有你的联系人和真实应用状态。
- 本项目要的就是“你自己的真机、你自己的登录”，代价是通道要自己搭：无线调试配对、反向隧道、adb 转发，这三步缺一不可。

## 为什么不用 Termux 当控机通道

Termux 是手机上的 Linux 环境，能跑脚本、能发 Termux 通知、能向服务器推文件，但：

- adb shell 跑的是另一个用户，进不了 Termux 的私有目录，跑不了 termux-* 命令（实测权限拒绝）。
- Termux 通知是标准通知，不是 Android 16 实时更新，上不了流体云药丸（实测结论，见阶段通知文档）。
- 所以 Termux 在本项目里只适合做文件同步、定时采集这类事，界面操控走 adb + phone-harness。

## 失败时先查什么

1. 隧道还在吗：服务器本机反向隧道端口有没有监听。
2. adb 设备还在吗：`adb devices` 是不是 device（已授权）状态。
3. 手机在哪个界面：读屏看当前是列表还是某个会话，不要假设。
4. 输入框里有什么：超时、中断后重跑之前，必须先查输入框，避免重复输入。
5. 输入法是谁：任务结束必须恢复回原始输入法，并读设置核对一次。
