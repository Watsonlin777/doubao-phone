# 对抗性审查：Jev 手机任务优化方案（截至 2026-10-27）

审查范围：skill v1.3.13–v1.3.17 五类影子附录、Stage 1–5 spec 与离线脚本、
3 趟真实手机任务（20261027-1644、1705、1725）、16 行真实影子快照、
16+1 条 TypeSafe 真实 Jev 对照（模型 jev-1.14.0）、评估备忘。
审查立场：假设方案是错的，找它在什么条件下会误发、误判、误报效率、误导上线。

## 结论先说

目前不能上线任何一类 Jev 判断。不是因为 Jev 完全没用，而是因为现有证据
只能证明“Jev 在薄摘要上倾向保守”，不能证明“Jev 在真实屏上能安全替代或辅助老逻辑”。
最危险的不是 Jev 判错一次，而是把一次薄摘要对照误读成验证，从而放宽确定性核对。

## 致命档（会直接动摇上线结论）

1. 影子快照本身无法独立验证。
   快照只含布尔值与耗时，不含屏上原文。Jev 对标题、输入、发前门、发后这几类
   给出的 unknown（noul 0.51–0.73）不是 Jev 能力不足的证明，也不是安全证明，
   而是“证据不足”的必然结果。反过来，如果未来为了让 Jev 能判，就把屏上原文
   （联系人、消息内容）喂给 Jev，那就把隐私风险重新引进来，且目前方案里
   没有对这种喂法的数据最小化、脱敏、留存、训练用途的核查。两头都走不通，
   是方案设计本身的矛盾，不是样本不够就能解决的。

2. 样本全部是成功样本，安全结论无法证伪。
   16 行老逻辑全为通过：标题全 true、输入全 true、下一步全 proceed、发前门全 true、发后全 true。
   没有标题错误、输入框非空、草稿、锚点缺失、停下、重读、W3 横幅、发送失败样本。
   因此“Jev 从未误放行”这句话在现有数据里是空真：Jev 从未有机会误放行。
   正常成功趟再跑多少次也不会补齐失败样本，失败样本必须靠受控失败/遮挡场景单独设计与授权，
   否则上线讨论永远缺最关键的一半数据。

3. 状态措辞会泄露老逻辑结果，等待类的“干净 pattern”可能是循环论证。
   等待对照里，读回成功时 Jev noul 0.86–0.87，读回失败时 0.10。
   这看起来很干净，但状态里直接写了“readback succeeded / did not succeed”，
   Jev 很可能只是把“读回成功”当成“稳定”的代理，而不是独立判断了屏幕是否稳定。
   同理，下一步的 proceed 置信度 0.88/0.89，也可能来自任务语境默认倾向继续，
   而不是来自核对是否通过的证据——状态里根本没写核对是否通过。
   一旦把这种对照当成“Jev 判断准确”，上线后遇到核对失败、读回失败的真实场景，
   Jev 仍可能因语境倾向而判 proceed。

4. 阈值是拍出来的，没有校准。
   0.80、0.85、0.90、0.95 没有 ROC、没有 Jev 概率校准检验、没有不同问题措辞下的灵敏度分析。
   实测里 Jev noul 在不同问题上天然分布不同：等待 0.86–0.87、标题 0.52–0.54、
   发前门 0.61、发后 0.66。同一阈值 0.90 用在标题上几乎永远 unknown，用在等待上几乎永远 match，
   这说明阈值反映的是问题难度与措辞，而不是统一的安全标准。
   发前门 0.95 尤其如此：按现有分布，它上线后几乎永远 unknown，等于没上线；
   若为了让它能判而降低阈值，又等于放宽最靠近发送的门。

5. 效率前提可能错了方向。
   真实趟总时长 743–944 秒，Jev 单条 0.7–2.8 秒。即使 Jev 每步都判对，它省下的也只是
   “是否重读”这一次判断，而不是启动 213 秒、标题阶段 135 秒、输入阶段 289 秒这些大头。
   阶段间间隔 75–131 秒的来源至今没有逐决策拆解，step_seconds 又不可信（见下），
   所以“Jev 能优化手机任务”这个总前提在现有数据里根本没有被检验过。
   真正的瓶颈可能是 Hermes 启动后第一次工具调用前的推理段，而不是某一次核对判断。

## 高风险档（上线前必须修，否则会误导）

6. P2 问错问题暴露了问题审查流程的薄弱。
   P2 本应问读回相等，却问了是否为空，dry-run 的合成数据没有 catch 住，
   因为合成数据只检查阈值逻辑，不检查问题与决策点的语义对应。
   同类风险仍存在于其他问题：标题问题需要预期名与屏上名两个输入，快照里一个都没有；
   发前门问题需要收件人、内容、用户确认三项，快照里也都没有；
   下一步的 proceed/re-read/stop 定义里，“发送”被刻意排除，但老逻辑的 N2 本质上就是走向发送，
   把发送排除在选项外并不能消除“proceed 被误读成可以发送”的风险。

7. step_seconds 与 wait_stable_result 不可信，效率评估会建立在假数据上。
   run 1725 里标题、输入、下一步、发前门各点的 step_seconds 出现重复值
   （首次 1.848 秒、二次 1.5 秒），很可能是 agent 复用了同一段时间或估算，
   而不是逐点实测。wait_stable_result 6 行全为 false，也与“后续读屏成功、任务继续”
   的事实不一致，说明该字段的语义在 skill 里没有讲清，agent 各自理解不同。
   用这样的数据去算“省了多少秒”，结论一定是假的。skill 必须明确规定逐点
   before/after 时间戳的取法，并由看门狗或离线脚本校验重复值、异常值，否则不要用耗时字段。

8. skill 附录越加越长，执行一致性没有保障。
   skill 已到 839 行，五类附录都在文末，agent 是否每次都读到、读懂、按附录记，
   目前只有“run 1725 五类都记到了”这一个正面证据，没有反面测试：
   没有测试过附录被忽略、记错字段、记错文件、记录失败时是否真的忽略继续、
   也没有测试过标题/输入/发前门附录在失败场景下的行为。看门狗不监控影子文件，
   所以影子缺失是静默的——W3 0 行到底是“没触发”还是“没记上”，现在无法区分。

9. 模型与环境漂移没有钉住。
   Jev 返回模型是 jev-1.14.0，而早期文档里是 jev-1.13 / jev-1.13-free，
   模型版本、Antigravity 模型目录（43 个，动态）、Hermes 版本、skill 版本都在变，
   但对照里没有把“模型版本 + 问题措辞 + 阈值”作为一组固定基线钉住。
   下次模型一变，noul 分布一变，之前定的阈值就失效了，却不会有任何告警。

10. 隐私与第三方数据用途没有核查。
    TypeSafe 的 Jev 输入留存、训练用途、日志保留期，在本方案里没有以官方文档或账号页为准核查过。
    现在只发布尔值，风险低；但一旦为了提高 Jev 准确率而加屏上文本，风险会立刻变高，
    而且手机任务数据属于敏感数据（联系人、消息、微信界面），不能默认走“只要不发原文就安全”的口径。
    未来任何加字段的改动都应单独做隐私审查，而不是在影子附录里顺带加上。

## 中风险档（会影响结论质量，但不直接导致误发）

11. 泛化范围极窄。
    全部是文件传输助手自测、内容“你好”两个字、默认 medium、同一台手机、同一网络条件。
    真人、真群、长句、候选词复杂、输入法切换失败、隧道抖动、横幅遮挡等场景一个都没覆盖，
    不能把自测结论推广到真实任务。

12. Jev 延迟与成本被低估了上线后的量。
    现在是离线 16 条、每条约 1 秒、token 约 300+20。若上线后每步都问 Jev，
    一趟可能问 10–20 次，延迟与 token 仍小，但若 Jev 超时、451、限流、模型不可用，
    回落老逻辑的路径至今没有实测过。spec 里写了回落，skill 里没有写回落的触发条件与超时，
    也没有测试过回落时是否会把“Jev 不可用”误读成“unknown 即停下”从而无故中断正常任务。

13. 屏幕内容注入风险没有考虑。
    未来若把屏上文本喂给 Jev，联系人备注、消息内容、群名里若含有指令性文字，
    可能影响 Jev 的 choice/noul，即使 Jev 只做决策不写文本，也可能被诱导判 proceed。
    状态构建必须做清洗与隔离，不能把原始屏文本原样当成 Jev 的 state。

## 建议的修复顺序（按风险，不按阶段顺序）

1. 先钉住问题语义审查：每个问题配一张“决策点—问题—所需输入—禁止输入”对照表，
   由第二人（或独立脚本）检查问题与决策点是否对应，P2 这类错误不能再靠事后发现。
   同时修 skill 里 step_seconds 与 wait_stable_result 的取法，并加重复值校验。
2. 再补失败样本，而不是多跑成功趟：单独设计并授权受控场景——标题错误停下、
   输入框非空停下、横幅遮挡重读、锚点缺失停下——每类至少拿到失败样本后，再谈误放行。
   正常成功趟只用于补充通过样本，不能替代失败样本。
3. 再决定影子数据的取舍：要么承认布尔值快照只能做保守性检查（unknown 为主），
   上线目标只能是“Jev unknown 时多重读一次”，不能是“Jev match 时省掉核对”；
   要么单独做隐私审查后，决定是否给 Jev 加脱敏后的屏上证据，并重新校准阈值。
   两条路不能混着走，更不能在没做隐私审查的情况下偷偷加字段。
4. 最后再谈上线：每类单独验收，标准仍是原三条——样本足够、误放行零、效率多次实测支撑，
   且必须加上第四条：模型版本与问题措辞钉住、回落路径实测通过、看门狗能发现影子缺失。
   任何一类不满足，就只停那一类，不影响其他类。

## 一句话 verdict

方案的影子记录本身做得干净（备份、diff、只记布尔值、不改主流程、不切换），
但它目前只能证明“记录系统能跑通”，不能证明“Jev 判断值得信任”；
在失败样本、屏上证据、阈值校准、耗时可信度这四个缺口补齐之前，任何一类都不应上线，
否则就是把薄摘要对照误读成验证。
